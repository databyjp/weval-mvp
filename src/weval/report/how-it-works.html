${logo}How weval works

weval gives a coding Agent a real Weaviate job, scores what it leaves behind, and keeps enough of each Trial to explain the score later.

Scores come from a snapshot

verify.py captures the live stack before the Trial environment is torn down, so any Trial can be re-scored later.

Runs are kept, then read

weval check, analyse, and report read retained runs. None of them starts a Trial or changes a recorded score.

Like is compared with like

Fingerprints keep a Treatment's Trials beside baseline Trials of the same Task and check versions.

Terms such as Task, Agent, Treatment, and Trial are defined in the glossary.

One run

weval run runs one Task with one Agent, with or without a Treatment, for n Trials.

weval runs on your machine. Harbor starts one Trial environment per Trial, on Modal or, with --local, on the local Docker daemon.

  1. 1
    Package: build the Task package and fingerprint it.

    The packaged prompt is the Task's instruction.md, or the Treatment's replacement prompt, followed by the shared Trial-environment notes. tests/ gets the shared verify.py and the Task's snapshot.py and check.py. A Treatment's skills are installed for the Agent.

  2. 2
    Harbor Job: start n Trials of one Agent at once.

    Each Trial gets its own environment, built from the Task's environment/ and weval's Compose overlays.

  3. 3
    Agent: work in /app until done or out of time.

    The Agent works beside a Weaviate stack until it stops or hits the Task's time limit. Harbor then copies /app to artifacts/submission/.

  4. 4
    verify.py: snapshot the live stack, then score the snapshot.

    It starts the submitted Compose stack, and the application when the Task has one, then calls the Task's snapshot() and scores the result with check.py. The reward is 1 only when every required check passes; preferred checks are reported but do not affect it.

  5. 5
    Record: write weval.json for each Trial.

    It holds the Trial's status, each check's result, the Agent's token use and cost, and the fingerprints described below.

  6. 6
    Redact, label: scrub credentials, then explain each failed check.

    weval replaces credential values in every retained file. A step finder picks the transcript steps behind each failed check, and Jev labels why the Agent made that choice and where its answer came from. Labels never change a score.

After the runs

Re-score, compare, and publish retained runs without running new Trials.

CommandUse it when
weval checkYou changed a Task's check.py, or want one Trial's diagnostics and labels.
weval analyseA batch of baseline and Treatment runs has finished.
weval reportYou want to read the results. Rebuild it after any run, analysis, or note.

Versions and comparisons

A change to check.py needs only a re-score. Any other change to a Task or Treatment needs new Trials.

Each Trial records three fingerprints, content hashes of what it was given. They decide what a change costs and which Trials are compared.

FingerprintCoversAfter a change
taskThe Task directory except check.py, plus the shared notes, verify.py, and Compose overlaysRun new Trials. The index shows only each Task's current version; earlier versions move to the bottom of the Task page.
checkThe Task's check.pyRe-score retained Trials with weval check.
treatmentThe Treatment's skills and its replacement prompt for this TaskRun new Treatment Trials.

A Treatment comparison pairs Treatment Trials with baseline Trials of the same Task, Task version, and check version, so a Treatment is never compared against Trials scored by a different check.py.

Reading a result

A status says whether a Trial produced a scored outcome. A class says what a failed check means.

Trial status

passedEvery required check passed.
failedThe verifier scored the Trial and a required check failed, including when the snapshot itself failed.
timed-outThe Agent hit a Harbor limit, but the verifier still scored the submission. It does not count as passed.
non-resultInfrastructure, or a failed model request, prevented a valid outcome. Not a finding.
incompleteAn expected log or the submission is missing. Not a scored result.

Failure class

agent gapThe Agent missed something it could have discovered.
Weaviate gapThe product or its docs led the Agent astray.
scorer bugsnapshot.py or check.py misjudged a correct solution.
Task defectThe prompt or workspace hid or contradicted a scored constraint.

A failed check is a finding, not a defect to remove. Only scorer bugs and Task defects call for a change to weval.

Scoring and analysis

A check decides pass or fail. Everything after it explains the failure, and none of it changes the score.

Each layer reads less than the one before, so a later answer can be traced back to the evidence it was given.

LayerRun byReadsProduces
Scoreverify.py, in the Trial; weval checksnapshot.jsonPass or fail per check, with a failure message naming what was observed. A failed snapshot fails every check; the report counts that Trial in the pass rate but in no check's failure rate.
DiagnoseCode, whenever a Trial is readThe trace, application.logWhether the agent was shown the check's expected value, whether a Treatment skill loaded, and Weaviate deprecation warnings.
LabelTwo models, after weval run and weval checkThe traceFor each failed check: the step where the agent decided, why, and where its answer came from.
AnalyseA model and a rule, in weval analyseComputed facts for one Treatment comparison, never transcriptsFailure patterns with a proposed class each, and where the model and the rule disagree.

Labelling a failed check

One model finds the steps that matter. A second model reads only those steps and answers two fixed questions.

  1. 1
    Step finder: pick the steps behind each failed check.

    A long-context model (STEPS_MODEL in labels.py) reads the whole trace once per Trial. For each failed check it names the decision step, where the agent made the choice the check found, and every other step that bears on it, each tagged source, intent, trigger, or verification. Finding no relevant steps is a valid answer.

  2. 2
    Jev: answer two Choice questions from those steps alone.

    Cause asks why the agent made the choice (table below). Answer source asks where the value came from. The options are each URL, search, or Treatment file that the selected steps showed the agent, plus the agent's own knowledge.

  3. 3
    Labels: saved per Trial and reused.

    Each answer carries Jev's confidence from 0 to 1. Treat one below about 0.5 as "check by hand". Labels are saved in <run>/labels/<trial>.json, keyed by a hash of the request, so they are asked again only when the failed checks, the trace, or the prompts change. A Trial whose snapshot failed is not labelled, because no value was observed to trace.

CauseThe agent...
no_lookupchose without looking anything up.
followed_sourcetook the choice from something it was shown, such as a docs page, a search result, a skill file, or example code.
ignored_current_practicewas shown the current practice the check looks for and chose otherwise without saying why.
considered_and_rejectedweighed the option the check looks for and chose otherwise, giving a reason.
environment_forcedwas pushed to the choice by an observation, such as an error or a failed health check.
no_trace_evidenceleft no explanation in the steps shown.

Proposing a class

A model and a hand-coded rule each propose a class from the same facts. Where they disagree, a person decides.

The rule, first match winsProposed class
The check defines no expected valueunclassified
The snapshot did not record the expected valueinfrastructure failure
No trace to say what the agent was shownunclassified
The agent was shown the expected valueagent gap
It was not, and Jev's answer source is a Weaviate pageWeaviate gap
Otherwiseunclassified

Each finding in the report shows the analyst's patterns, the rule's proposals, any disagreement, and the labels for each failing Trial. The report renders these as saved; it never calls a model.
